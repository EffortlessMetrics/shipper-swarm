# Migrating to Shipper 0.5.0

Status: **pre-release compatibility guidance**

This guide covers the source, configuration, durable-artifact, command, and
operator changes that may require action when moving from 0.4 to 0.5. It does
not claim that 0.5.0 is published or publicly installable.

## Rust source compatibility

### Initialize registry policies

`RuntimeOptions` has an additive public `registry_policies` field. Downstream
code that constructs the type with a struct literal must initialize that field
or migrate to its own constructor/default pattern. This is a source migration
even though existing serialized artifacts remain readable.

### Account for new event variants

The public event vocabulary includes additive records such as
`PackageUploaded` and other evidence/recovery variants. Exhaustive matches must
handle the new variants. The governed enum round-trip proof protects the wire
names; it does not make an exhaustive downstream match forward-compatible.

### Recheck the 13-crate train

The retained semver evidence describes the exact historical candidate it ran
against. Library consumers should run their own build/tests against the final
0.5 artifacts. Release authority must rerun the configured semver gate on the
final approved SHA before publication.

## Durable artifacts

### Events are authoritative

`events.jsonl` remains authoritative, `state.json` is a projection, and
`receipt.json` is a terminal summary. `PackageUploaded`, pending
reconciliation, attempt details, `execution_result`, and rerun/resume safety
add fields or records to the 0.5 evidence set. When sources disagree, Shipper
fails closed rather than trusting a stale projection or receipt.

Do not read package state from `.packages[].status`; the state value remains at
`.packages[].state.state`.

### 0.4 reads and 0.5 forward compatibility

Real 0.4 state, events, receipts, reconciliation evidence, and encrypted
artifacts are covered by retained load/replay/resume proof. Missing evidence
that an older format could not record remains unknown; it is not synthesized.

The reverse direction is not promised: a 0.4 binary may not understand every
new 0.5 event variant, field, state, receipt value, or command envelope. Keep a
copy of durable evidence before changing the binary used for an active run.

### Encryption migration

New encrypted writes use versioned KDF v2 PBKDF2-HMAC-SHA256 parameters at
600,000 iterations. Legacy unversioned v1 artifacts remain readable at their
original 100,000-iteration cost and are upgraded when rewritten. Preserve the
same passphrase source and state directory; no recovery claim extends beyond
the tested artifact and key inputs.

### Inspect drilldowns

Raw `PublishEvent` JSONL and direct versioned `Receipt` serialization remain
governed recorder/evidence surfaces. 0.5 does not introduce a command-owned
aggregate inspect JSON envelope, footer, or broader support promise for them.

## Configuration and registry behavior

- Custom registries must provide the required index/destination policy rather
  than inheriting crates.io defaults.
- Private or loopback destinations require explicit permitted posture, and
  rehearsal/local exceptions do not silently authorize production publish.
- Strict ownership validates tokens for every selected registry before any
  registry query or package operation.
- Singular `--registry` remains supported. `--registries` and
  `--all-registries` are rejected with `status --durable` before evidence is
  read, because the durable state directory is not safely segregated for those
  selectors.
- The existing `parallel.per_package_timeout` key controls both sequential and
  parallel package operations for one migration cycle.

## CLI and CI behavior

### Exit codes

| Exit | Meaning |
| --- | --- |
| `0` | The command completed successfully for its documented outcome. |
| `1` | Complete failure, unsafe/inconclusive evidence, malformed evidence, or another operational error. |
| `2` | A Shipper partial result only when the command-owned evidence says continuation is safe; Clap also uses `2` for usage errors. |

Do not branch on exit `2` alone. Parse the command-owned versioned JSON outcome
when automation needs to distinguish a partial result from a parser error.

### Human and JSON parity

Plan, preflight, doctor, non-watch status, durable status, publish, and resume
derive human and JSON guidance from the same typed outcome. Automation should
prefer the versioned JSON schema and still treat unknown enum/string values
fail closed.

Ordinary status is a transient registry-aware view. `status --durable` is a
separate local-evidence mode, conflicts with `--watch`, performs no registry
query, and emits `shipper.status.durable.v1` for JSON output.

Generated resume guidance is emitted only when the required manifest, config,
registry, and state-directory context can be preserved. Otherwise the outcome
describes the safe posture without inventing a replay command.

## Recovery and liveness

- Terminal `ExecutionFinished` evidence structurally dominates lock liveness.
- An unfinished run is live only on Linux when the captured boot ID, PID
  namespace, PID, and process-start ticks match a stable double-sampled probe.
- A missing process can be `NotLive` only inside the same proven boot and PID
  namespace. Legacy, cross-host, unsupported, unreadable, malformed, reused,
  or contradictory identity is unknown.
- Exact identity is not downgraded merely because a legitimate run is old.
- Existing `acquire_with_timeout` lock stealing remains age-based and is not
  made liveness-aware by the read-only observation feature.

Resume only when event/state/receipt/reconciliation identity and consistency,
plan identity, unfinished posture, and safe liveness predicates all agree.
`StillUnknown`, corruption, disagreement, or missing required identity is a
stop-and-investigate result.

## Release-maintainer changes

0.5.0 and earlier are an opaque pre-Changie baseline. Edit `CHANGELOG.md` and
`.changes/0.5.0.md` together, use exactly Changie v1.25.1, and run
`cargo changelog-roundtrip` before and after. Never run
`changie batch 0.5.0`.

The release workflow now binds approved source, reviewed release notes,
reversible proof, four target binaries, tag/resume identity, public version
verification, and workflow authority. These are preparation gates, not
publication authorization.

## Before promotion

1. Run application and embedding tests against the final candidate.
2. Preserve active 0.4 evidence before changing binaries.
3. Update struct literals and exhaustive event matches.
4. Validate every custom registry and credential posture.
5. Distinguish command partial results from Clap usage errors.
6. Follow the [release preparation checklist](release-preparation-checklist.md)
   and record exact SHA, tree, workflow, binary, and rehearsal evidence.

The actual release date and public-artifact links are added only in release
authority after the separately reviewed candidate is approved.
