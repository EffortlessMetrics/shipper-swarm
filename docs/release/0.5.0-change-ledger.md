## Field vocabulary

Every source row carries the issue-required fields in compact form:

- Audience: `U` CLI user, `O` CI operator, `L` library consumer, `R` release or
  security operator, `M` maintainer, `X` mixed.
- Importance: `H` headline, `D` detailed, `M` maintenance, `O` omit.
- Kind: `added`, `changed`, `fix`, `security`, or `removed` records a product
  disposition directly. `merge`, `docs`, `test`, and `maintenance` retain the
  source row's integration shape; #269 normalizes those to `changed` when it
  writes public prose instead of presenting integration mechanics as features.
- Compatibility: `none`, `additive`, `source`, `config`, `behavior`,
  `artifact`, or `operational`.
- Destination: `CL` changelog, `RN` release notes, `MG` migration guide, `PD`
  public docs, `MT` maintenance record, or `OM` omit from public narrative.
- Disposition: `promote`, `consolidate`, `retain`, `historical`, or `omit`.
- Follow-up: every row is consumed by editorial issue #269. A row names an
  additional issue only when work beyond that common editorial follow-up is
  required; otherwise its additional follow-up is `None`.

The compact `ST01` through `ST10` row references resolve to the stable
`REL050-ST01` through `REL050-ST10` canonical IDs below.

## Pre-release facts versus post-publication facts

May be stated before publication: merged behavior, compatibility surface,
bounded test and CI evidence, source/review identities, current support tier,
and preparation blockers. Must wait for release authority: final version date,
approved/tag SHA equality, crates.io success, GitHub Release state, signatures,
SBOM/provenance artifacts, install-from-public-registry proof, and downstream
availability. Historical candidate proof never becomes post-publication proof
by repetition.
