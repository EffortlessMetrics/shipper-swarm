## Contract and authority

- Engine execution results, events, state, receipts, reconciliation, and
  identity validation remain the semantic authorities. CLI outcome adapters
  must not reconstruct a competing state machine.
- `events.jsonl` is authoritative, `state.json` is a projection, and
  `receipt.json` is a completed-run summary as specified by
  `docs/INVARIANTS.md`.
- `SHIPPER-SPEC-0004` owns compatibility for the stable command envelopes it
  lists. It does not currently define an `inspect-events` or `inspect-receipt`
  command-owned JSON envelope. `SHIPPER-SPEC-0005` and `SUPPORT_TIERS.md`
  separately own the stable/internal recorder behavior for complete events,
  corruption handling, redaction, and events-as-authority recovery.
- `ActionKind` and `OperatorAction` are the shared crate-private vocabulary.
  Command-specific private outcome structs adapt their own authoritative
  evidence. This is the accepted semantic-equivalence and DRY boundary for
  #274: shared meaning lives once, while command evidence stays with its owner.
  A monolithic or public `OperatorOutcome` type is not required.
- Status without `--watch` reports transient registry visibility. It does not
  load authoritative run evidence and cannot establish safe rerun, safe
  resume, interruption, ambiguity, or terminal run truth.

## Resolved #274 decisions

### Inspect commands remain evidence-only drill-downs

`inspect-events` and `inspect-receipt` satisfy #274 only as drill-down evidence
surfaces referenced by other operator outcomes:

- `inspect-events` currently emits one raw serialized `PublishEvent` per JSONL
  record. That serialization shape is characterized behavior, not a
  command-owned versioned schema, footer, or envelope. Its stable/internal
  recorder guarantees remain owned by `SHIPPER-SPEC-0005` and
  `SUPPORT_TIERS.md`: complete-event streaming, actionable corruption,
  redaction, and events-as-authority behavior must not regress.
- `inspect-receipt` currently parses and serializes the versioned `Receipt`
  value directly. The receipt type owns that version and its existing evidence
  contract; the command does not own a second JSON envelope.
- Neither command receives an outcome/footer in this closeout. Any future
  promotion must be separately versioned and classified under
  `SHIPPER-SPEC-0004` and `SUPPORT_TIERS.md`.

This decision preserves the existing stable/internal recorder behavior and
raw-evidence consumers without promoting the current JSON serialization shape
into a command-owned versioned envelope. It also keeps evidence truth separate
from operator guidance: drill-down output is not, by itself, a typed answer
about whether a run is live, terminal, interrupted, ambiguous, or safe to
resume.

### Shared vocabulary plus private adapters is sufficient

The crate-private `ActionKind` and `OperatorAction` vocabulary is the shared
semantic model required by #274. Plan, preflight, publish, resume, status, and
doctor may retain command-private outcome adapters because their evidence and
compatibility envelopes have different owners. Those adapters must reuse the
shared action identity and must derive both human and JSON guidance from the
same command outcome object.

This is semantic equivalence, not structural uniformity. It avoids duplicated
action meaning without inventing a public embedding promise or forcing unlike
receipt, registry-visibility, readiness, and planning evidence into one
monolithic struct.

## Remaining #274 implementation gap

The inspect compatibility and shared-model decisions above are resolved. One
product gap remains: the primary `status / inspect` journey does not yet derive
a typed operator outcome from durable run evidence. #325's non-watch status
outcome is intentionally limited to transient registry visibility, while the
raw inspect commands expose evidence without interpreting it.

The follow-up implementation packet is:

| Field | Required boundary |
| --- | --- |
| Owner | `shipper-cli` command adapter. `shipper-core` events, execution state, receipt, reconciliation, identity, and any affirmative liveness signal remain authoritative; expose only a narrow read projection if the adapter cannot consume an existing owner. A live classification requires a core-owned liveness authority with defined stale and cross-host semantics. |
| Likely surfaces | `crates/shipper-cli/src/lib.rs` around `run_status`, `run_status_watch`, `run_inspect_events`, `run_inspect_receipt`, and the command outcome adapters; `crates/shipper-cli/tests/e2e_status.rs`, `e2e_expanded.rs`, and `bdd_workflow.rs`; existing `shipper-core` state/event/receipt readers for authority proof. |
| Required semantics | Classify durable run truth as terminal, interrupted, ambiguous/`StillUnknown`, safely resumable, identity-mismatched, or live only when affirmative core-owned liveness authority proves it. Without that authority, report unknown/possibly interrupted. A fresh or existing lock, `ExecutionStarted`, state timestamp, or file freshness alone must never prove live. Events win when state or receipt disagree. Transient registry visibility remains a separate observation, not a safety claim. |
| Focused proof | Table-drive all semantic states including a crashed publisher with a fresh lock/no terminal event, no-state, corrupt/stale evidence, disagreement, and opposite paths. Prove the crashed/fresh-lock case fails closed to unknown/possibly interrupted unless the core liveness authority is affirmative. Spawn independent human and versioned-JSON invocations with semantic parity, bounded timeouts, no new release side effects, valid command/commandless posture, configured-path identity, and recursive secret-sentinel scans. |
| Compatibility | Select and document a compatible versioned command surface under `SHIPPER-SPEC-0004`; do not append a footer to raw event JSONL, wrap direct receipt rendering implicitly, or silently redefine existing transient `shipper.status.v1` fields. Preserve the SPEC-0005/support-tier recorder guarantees for complete events, corruption diagnostics, redaction, and events authority. |
| Non-goals | Runtime work in this docs PR; a new public outcome type/crate; changing engine truth; receipt/event/state schema changes; aggregate multi-registry JSON; auto-remediation/retry; release, tag, publication, credential, or #268-#271 closure work. |

Issue #329 implements this gap as a mutually exclusive `status --durable`
mode with a new `shipper.status.durable.v1` envelope. Dispatch must occur
before registry-client construction and queries. Ordinary `status.v1`,
`status.watch.v1`, raw event JSONL, and direct Receipt JSON remain unchanged.
The CLI uses the narrow unsupported core bridge described above and one
private outcome object for both human and JSON guidance. The gap remains open
until that candidate receives exact-head proof, review, merge, and
post-merge reconciliation.

The core prerequisite may affirm liveness only on Linux when a private lock
record and a stable observation agree on hostname, plan ID, boot identity, PID
namespace, PID, and process-start ticks. Other platforms and incomplete,
legacy, cross-host, changing, or unreadable evidence remain unknown. This
observation does not change lock acquisition: `acquire_with_timeout` continues
to reclaim locks by age alone and can therefore remove a lock held by a
long-running live process. It does not make lock stealing liveness-aware, and
an observational `not_live` result does not establish that resume is safe.
