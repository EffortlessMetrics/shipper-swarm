## Contract and authority

- Engine execution results, events, state, receipts, reconciliation, and
  identity validation remain the semantic authorities. CLI outcome adapters
  must not reconstruct a competing state machine.
- `events.jsonl` is authoritative, `state.json` is a projection, and
  `receipt.json` is a completed-run summary as specified by
  `docs/INVARIANTS.md`.
- `SHIPPER-SPEC-0004` owns compatibility for the stable command envelopes it
  lists. It does not currently define an `inspect-events` or `inspect-receipt`
  command-owned JSON envelope. `SHIPPER-SPEC-0005` and `SUPPORT_TIERS.md`
  separately own the stable/internal recorder behavior for complete events,
  corruption handling, redaction, and events-as-authority recovery.
- `ActionKind` and `OperatorAction` are the shared crate-private vocabulary.
  Command-specific private outcome structs adapt their own authoritative
  evidence. This is the accepted semantic-equivalence and DRY boundary for
  #274: shared meaning lives once, while command evidence stays with its owner.
  A monolithic or public `OperatorOutcome` type is not required.
- Ordinary status without `--watch` or `--durable` reports transient registry
  visibility. It does not load authoritative run evidence and cannot establish
  safe rerun, safe resume, interruption, ambiguity, or terminal run truth.
- `status --durable` reads authoritative local run evidence without registry
  access and renders `shipper.status.durable.v1`. It does not redefine
  ordinary `shipper.status.v1`, `shipper.status.watch.v1`, raw event JSONL, or
  direct Receipt JSON.

## Resolved #274 decisions

### Inspect commands remain evidence-only drill-downs

`inspect-events` and `inspect-receipt` satisfy #274 only as drill-down evidence
surfaces referenced by other operator outcomes:

- `inspect-events` currently emits one raw serialized `PublishEvent` per JSONL
  record. That serialization shape is characterized behavior, not a
  command-owned versioned schema, footer, or envelope. Its stable/internal
  recorder guarantees remain owned by `SHIPPER-SPEC-0005` and
  `SUPPORT_TIERS.md`: complete-event streaming, actionable corruption,
  redaction, and events-as-authority behavior must not regress.
- `inspect-receipt` currently parses and serializes the versioned `Receipt`
  value directly. The receipt type owns that version and its existing evidence
  contract; the command does not own a second JSON envelope.
- Neither command receives an outcome/footer in this closeout. Any future
  promotion must be separately versioned and classified under
  `SHIPPER-SPEC-0004` and `SUPPORT_TIERS.md`.

This decision preserves the existing stable/internal recorder behavior and
raw-evidence consumers without promoting the current JSON serialization shape
into a command-owned versioned envelope. It also keeps evidence truth separate
from operator guidance: drill-down output is not, by itself, a typed answer
about whether a run is live, terminal, interrupted, ambiguous, or safe to
resume.

### Shared vocabulary plus private adapters is sufficient

The crate-private `ActionKind` and `OperatorAction` vocabulary is the shared
semantic model required by #274. Plan, preflight, publish, resume, status, and
doctor may retain command-private outcome adapters because their evidence and
compatibility envelopes have different owners. Those adapters must reuse the
shared action identity and must derive both human and JSON guidance from the
same command outcome object.

This is semantic equivalence, not structural uniformity. It avoids duplicated
action meaning without inventing a public embedding promise or forcing unlike
receipt, registry-visibility, readiness, and planning evidence into one
monolithic struct.

## Covered #274 durable implementation and retained boundaries

The inspect compatibility and shared-model decisions above remain resolved.
#330 and #331 close the durable product implementation gap: mutually exclusive
`status --durable` derives a typed `shipper.status.durable.v1` outcome from
core-owned run observation, state/event/receipt consistency, reconciliation,
and identity evidence without registry access. Human and JSON rendering share
one private outcome object. Ordinary status/watch, raw event JSONL, and direct
Receipt JSON remain unchanged.

The implementation remains deliberately bounded:

- Affirmative liveness is Linux-only and requires exact agreement on hostname,
  plan ID, boot identity, PID namespace, PID, and process-start ticks. Other
  platforms and incomplete, legacy, cross-host, changing, unreadable, or
  malformed evidence remain unknown.
- `shipper_core::cli_bridge` is doc-hidden, additive, unsupported, and not
  re-exported by the `shipper` facade. It exposes no lock record, probe, or
  event-fold internals.
- `acquire_with_timeout` still reclaims locks by age alone and can remove a
  lock held by a long-running live process. Observation does not make lock
  stealing liveness-aware, and `not_live` alone does not prove resume safety.
- Durable status does not add aggregate multi-registry JSON. Multi-registry
  selectors are rejected before evidence reads; a singular registry remains
  supported.
- Proof uses bounded local fixtures and hosted Linux execution. It makes no
  real-registry, release, publication, tag, deployment, signing, or credential
  claim.

With these boundaries retained, #274 is product-complete. After this
reconciliation candidate passes its own review, hosted integration, merge, and
post-merge receipt gates, its only remaining external product/release closure
dependency is the #268 through #271 compatibility, migration, public
documentation, and support-tier integration.
